# Альтернативна блок-схема алгоритму рольового захисту

Ось інший варіант коду для PlantUML (більш класичний стиль блок-схеми):

```plantuml
@startuml
skinparam Monochrome true
skinparam DefaultFontName Arial
skinparam DefaultFontSize 12

title Рис. 2.2.2 – Блок-схема алгоритму рольового захисту маршрутів (Варіант 2)

start

:Отримання HTTP-запиту;
:Перевірка заголовка Authorization;

if (Токен знайдений?) then (ні)
    :Генерація помилки 401\n(Unauthorized);
    stop
else (так)
    :Декодування JWT за допомогою секретного ключа;
    if (Токен валідний?) then (ні)
        :Генерація помилки 401\n(Invalid Token);
        stop
    else (так)
        :Пошук користувача в базі за ID;
        if (Користувач існує?) then (ні)
            :Генерація помилки 404\n(User not found);
            stop
        else (так)
            :Додавання даних користувача\nдо об'єкта запиту (req.user);
            
            if (Чи є маршрут обмеженим за роллю?) then (ні)
                :Дозволити доступ (next());
                :Виконання контролера;
            else (так)
                :Порівняння ролі користувача\nзі списком дозволених ролей;
                if (Роль дозволена?) then (так)
                    :Дозволити доступ (next());
                    :Виконання контролера;
                else (ні)
                    :Генерація помилки 403\n(Forbidden);
                    stop
                endif
            endif
        endif
    endif
endif

:Повернення результату клієнту;
stop

@enduml
```

### Особливості цієї схеми:
1. **Стиль**: Використано класичний чорно-білий стиль (monochrome), що часто краще виглядає в друкованих роботах.
2. **Логіка**: Чітко розділено етапи "Пошук токена -> Валідація -> Пошук користувача -> Перевірка прав".
3. **Обробка помилок**: Кожен негативний сценарій завершується окремим блоком `stop` з вказанням коду помилки.
